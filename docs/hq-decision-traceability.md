## D3 invite rejoin target and current implementation

ADR 0060 accepts a generation-bound rejoin only for the exact disabled `member_left` membership. A rejoin invite binds the recipient User ID, Team/User leave generation and immutable issuance-time disabled-row snapshot. Fresh review and consumption also bind and recheck the exact current membership state or authoritative row absence; when present, the immutable issuance snapshot must still match at both stages and cannot be refreshed. Stale authority requires a new review. Legitimate never-left first invitations and existing enabled-member rules remain supported. The current API remains on the copied-token acceptance path: the in-app recipient list, decline action and durable leave generation are not implemented, and disabled memberships are still rejected. These D3/D9 rules remain implementation targets owned by HQ-703 and HQ-704.

## Supporting D1 context

D1's default is per-member sharing of only that member's eligible Conversation summaries (`lcm_leaves`). The target Team-side Project-owner binding is `workspace_projects.owner_team_member_id` and is independent of Team role; it does not promote a Project owner to Team role `owner` or grant Team-owner authority. Summary sharing, Curated Memory and Conversation Source Access have separate authorization boundaries.

Curated Memory is not included in the summary-sharing disclosure. Enabling it in an initial `shared_memory.pending_share` requires its own disclosure and ADR 0024 Step-up; later `shared_memory.change_fidelity` that enables Curated Memory requires the same separate disclosure and Step-up. Conversation Source Access also requires separate Step-up. Team-visible source is limited to the separately encrypted, sanitized ADR 0047 artifact and its verified allowed segments. The owner's raw private journal and original values removed by the Team-audience policy remain unavailable; source values that pass that policy appear only through the sanitized artifact.

The versioned Project Share Policy is enabled and revoked through exact Native review. Revocation stops future policy-based grant issuance only; existing grants continue under their own consent and lifecycle. It does not freeze, revoke or change their advancement. A grant freeze is a separate per-grant lifecycle action: it pins the last actually published revision and complete immutable authorized closure. If continuous Conversation Source Access is attached, the same atomic freeze pins its last authorized sanitized generation and segment frontier. Later material or bytes stay outside the frozen closure, unrelated grants remain unchanged, and restore or unsuppression cannot resume advancement or add material outside that closure.

See [ADR 0057](adr/0057-project-backed-workspaces-and-project-share-policy.md), [ADR 0024](adr/0024-tiered-desktop-action-approval.md), [ADR 0047](adr/0047-team-conversation-source-access.md), and [Project-sharing lifecycle](project-sharing-lifecycle.md). D1 is gated by HQ-001, HQ-701, HQ-702 and HQ-704. HQ-715 adds freeze coverage; HQ-702 depends on HQ-701, HQ-012, HQ-715 and HQ-008.

## D9 lifecycle ordering

The Team-side delete commits the Workspace Project tombstone, invalidates its Project links, freezes affected grants and attached continuous-source frontiers, archives the Project Thread, and stops Project progress before soft-deleting Team records. Project-scoped dispatch fails closed against a tombstone or unknown lifecycle state. The Workspace is not archived and grants are not revoked. Published recall remains available only to members who retain current access. The operation works while owner Desktops are offline and never writes their Personal databases; each owner's Desktop later detaches only that owner's chats to Just me and pauses that owner's Project Scheduled Jobs when it reconciles the tombstone.

Team leave checks the existing last-Team-owner guard before copy-back or destructive changes; if the actor is the last Team owner, refuse and use the existing ownership-transfer workflow. If no owned Workspace Project would be deleted, `team.leave` remains Native review. If any would be deleted, the target requires conditional Step-up bound to the exact Team/membership version, complete owned Project ID/version set and effects before mutation; stale state conflicts before copy-back. For every Project linked to the departing member, freeze that member's affected grants and invalidate only their link. If departure removes an owned Workspace Project, complete the Team-authoritative D9 effects for every member before deleting Team Project records or disabling membership: commit the tombstone, invalidate Project links, freeze affected grants/frontiers, archive the Project Thread, and stop Project progress and dispatch. Each owner's Desktop later detaches only that owner's chats to Just me and pauses that owner's Project Scheduled Jobs when it reconciles the tombstone. Team-side cleanup does not wait for offline owner Desktops and never writes their Personal databases.
