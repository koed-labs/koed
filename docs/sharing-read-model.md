# Sharing metadata read model

The Sharing view and `sharing_overview` agent tool use one owner-scoped Sharing aggregator on the authenticated Personal backend. Desktop reads `GET /v1/local-edge/sharing` through the typed Sharing IPC bridge. A managed Agent reads the same model through the execution-bound route described below. The route reads every backend in the owner's configured upstream registry that has enrolled Team Workspace read custody. Each backend is `available` with its current metadata or `unavailable` with a reason and the last successful read time known by this process. An unreachable backend does not produce an empty list.

For an available backend, the local edge reads `GET /v1/me/sharing` and `GET /v1/team-invites/mine` with the backend's enrolled device credential. The credential's local enrollment record must name the current Personal owner. Older records without that owner, or records with a malformed owner, are unavailable to Sharing until the owner enrolls again. The Team route derives visibility from current Team membership, Workspace access, and Project membership. It reports Project owners, groups, members, current invitations, direct Workspace access, access level, joined or invited status, Share Origin actor metadata, and per-item removal authority. `direct` on a Project member means an explicit Project membership link, with effective access limited by the Workspace grant. `direct` on Workspace access means an explicit grant to that person. The current backend has no inherited group path into a Project: Team membership alone does not grant Project access. The separate group name identifies the Team, not the source of a person's Project access. `through_group` is reserved for an actual inherited path if one is implemented later. A Project owner who is not a Team owner or admin may see an invitation associated with their Project, but `canCancel` is false. Only a current Team owner or admin can cancel an invitation; an owner invitation requires a Team owner.

The Personal edge overlays only the authenticated owner's `share_origins` rows, keyed by backend-qualified invitation or Workspace Access version. Conversation IDs never go to the Team backend. The response contains Team IDs and display names, not memory content, transcripts, credentials, or another member's Personal IDs. The renderer store clears its snapshot on owner or profile change and when stopped; focus or collaboration invalidation requests a fresh read. The boolean capability fields are display hints. Mutating routes recheck current authority and require their existing review.

The Team read also reports Project content counts from its repeatable-read visibility transaction. Sources are non-deleted Workspace Project source metadata excluding skills. To-dos are non-deleted, unfinished Workspace Project work items of kind `todo`. Chat summaries count distinct captured-session logical memories on Project-bound, active, unrevoked grants with a current or frozen LCM representation. "What the Project remembers" counts embedded semantic items from the same current or frozen representations, excluding invalidated, expired, blocked, and withdrawn items. The count represents Team-visible memory items, not the owner's Personal Project inventory. Older responses without content counts display unknown counts. Standalone Workspace access and Team invitations are displayed separately from Project membership; a Workspace grant alone does not imply Project access.

The page distinguishes current Project membership from administrative visibility. `joinedByMe` requires both the current member link and Workspace access; Team administrators who can inspect an unjoined Project are not shown as having joined it. Project filters and grouping retain their backend-qualified identity.

## Taking access back

The Sharing page offers the current action on each eligible row: remove a Project member, disable standalone Workspace Access, remove a Team member, or cancel a pending invitation. A Project owner can remove a Project member; Team owner or admin authority is required for an invitation or Team membership action. The existing Action Grant definitions choose each review tier. Project, Team membership, and Workspace Access removals require Step-up review; invitation revocation uses Native review. The review is the confirmation. Project removal names the target and explains that the person and their Agents lose access while what they added stays. Team removal lists the active Projects affected at review time and explains that their contributions stay. The Project share sheet uses the same removal coordinator.

An approved removal or invitation cancellation stays only in renderer memory for five seconds. Undo cancels its timer before a grant, access, or invitation mutation is sent. Quit, sign-out, backend or identity change, and renderer loss cancel pending work. HQ Desktop revokes renderer command trust immediately when quit starts, before asynchronous preview and service cleanup; a late timer cannot dispatch through IPC during shutdown. At dispatch the renderer checks the grant's approved state, unused state, and expiry; the Team backend checks them again.

For several targets, the coordinator reviews and finishes each target before the next review. It re-reads the Sharing model and Project lifecycle review, so a removal's Project version increment cannot invalidate a previously collected approval. Results distinguish done, failed with a reason, and not attempted. Recently shared is a 24-hour shortcut to these same actions; it does not limit removal eligibility. A transport retry sends the same immutable approved command, request ID, and Action Grant. The backend's consumed-grant receipt can replay the exact operation. If the outcome remains unknown, the UI refreshes the read model and reports the uncertainty without requesting fresh authority.

Each Sharing row carries its enrolled backend ID through the fresh authority read, review, Action Grant, and final command. The Desktop broker resolves that registered backend for this command without changing the active Team selection. The local edge still checks the owner's backend enrollment, scoped device credential, operation family, and current Team authority. Personal commands cannot use a row backend ID. A changed owner, profile, or device custody invalidates the pending action; selecting an unrelated active backend never redirects its reviewed command.

## Managed Agent tools and help

`sharing_overview` returns data from `GET /v1/managed-conversations/{executionId}/sharing-overview?executionGeneration=...`. Its version 1 result contains the unchanged page model in `overview` and backend-qualified Team administration data in `teams`. The latter uses the existing Team navigation and member-management reads. Only current Team managers receive management records. Self-removal and last-owner protections remain in place. Each read source reports availability separately; a missing roster cannot mean that a person has no access.

The MCP connection receives its execution, generation and loopback API address from the managed launch. These are not tool arguments. The runtime helper keeps the Desktop credential out of model input and results. The route verifies the current Personal owner, managed-execution credential, active command lease and generation, then checks them again after the read. Owner, credential, enrollment, backend-registry or profile changes invalidate the result. API Tokens cannot use this route. Person, Project and backend filters narrow the returned data while preserving every unavailable backend. Names are search labels, not cross-backend identity.

`sharing_remove` is a proposal receipt, not a completed mutation. Its exact targets carry backend and resource IDs. The Personal repository binds them to the original human command and rechecks current authority and versions before claiming the proposal. The HQ renderer uses the same removal coordinator and review services as the page. Its Sharing store stays active for the signed-in owner across HQ routes, and stops on sign-out, identity change or disable. Full access starts the required system review directly; Ask first shows the proposal first. Each selected target receives its own review and Undo window. Reading another enrolled Team for that review does not change the foreground selection or its cached snapshot.

Completion reconciles the selected targets through authorized reads. An unavailable backend or lost management authority cannot prove completion. Invitation cancellation requires the exact invitation lifecycle to be `revoked`; disappearance from the pending list is insufficient because an accepted invitation also leaves that list. Unknown outcomes never cause a fresh mutation. An Agent must identify ambiguous or unavailable scopes and cannot claim that every grant for one person was removed merely because its selected targets completed.

The versioned text in `packages/shared/src/sharing-help.ts` supplies both the Sharing panel and managed Codex, Claude and Pi instructions. Its committed mirror is `docs/how-koed-works.md`. Each promise names existing acceptance IDs. Pi loads this text through the managed runtime helper so its separately installed extension needs no workspace-package dependency. The tools and help add no backend answer synthesis.

Internal Shared Memory command failures keep their safe client error. Server diagnostics record only the operation, a bounded error class, an optional five-character database error code and up to four repository-relative source locations. They omit error messages, payloads, credentials and absolute host paths. Diagnostic collection cannot change the command result.
