# MCP Tasks feasibility

This report records the initial September 30 research checkpoint. Later work
implemented the shared delivery layer and the Pi, Claude Code, and opt-in Codex
adapters. It also corrected the runtime safety findings below. See
[asynchronous Memory Answers](async-memory-answer.md) for current behavior and
[the manual Codex tests](codex-deferred-recall-manual-tests.md) for remaining
validation. The findings below retain their original versions and scope.

Defer production adoption. A maintained SDK can delegate standard tasks to Koed's durable Personal runtime, and scoped client bridges can provide useful continuation. The current TypeScript server dependency, client support and delivery safeguards prevent adoption across the supported modes.

This investigation ran on September 30, 2026, against `ff5c7e1b926269bc40e5a13674d2ba574417831f` on `feat/async-memory-calls`. It changes no production behavior. All queries, answers and evidence were synthetic. Live model calls used the User-approved models. Real database experiments used separate encrypted PostgreSQL clusters, authenticated API operations and the actual Local AI Runtime.

Tickets 01–12 passed within their documented research limits. Ticket 13 produced decisive safety counterexamples and remains blocked for its subscription and diagnostic criteria. Ticket 14 uses that negative input as its criteria permit. [The ticket record](../tickets.md) retains those distinctions. A passing evidence validator does not mean that an unsafe behavior passes acceptance.

## Contract and maintained route

The selected contract is `io.modelcontextprotocol/tasks`, released snapshot `2026-07-28`, SEP-2663. Its source commit is `6c0997fbc040e6145c5cbd1e757aef9debb94303`. It differs from the experimental core Tasks proposal on `2025-11-25`. [Released specification](https://tasks.extensions.modelcontextprotocol.io/specification/2026-07-28/tasks), [pinned schema](https://github.com/modelcontextprotocol/ext-tasks/tree/6c0997fbc040e6145c5cbd1e757aef9debb94303/schema/2026-07-28).

A caller opts in on the request. The server can then return a task receipt with `resultType:"task"`, task ID, status, timestamps and required `ttlMs`. A receipt confirms acceptance before the answer is ready. Standard `tasks/get` returns current state and embeds the completed result. `tasks/cancel` acknowledges cooperative cancellation. `tasks/update` handles input responses, which this investigation did not exercise.

Application-error tool bodies are completed results. Execution and protocol errors are failed tasks. Cancellation intent remains working until execution reaches cancelled. The server can discard a task after its lifetime expires. Callers without Tasks support receive an ordinary result, or the missing-capability error when execution requires Tasks.

Released `ModelContextProtocol.Extensions.Tasks` 2.2.0 provides the working maintained server/client route. It depends on SDK 2.2.0, source `6fa3825973949a9c4f0cd8af344e15a8db09dc35`. `WithTasks(IMcpTaskStore)` supports delegated storage. The probe used .NET SDK 10.0.401 and acknowledged the package's experimental APIs. This does not select .NET for production. [Exact SDK documentation](https://github.com/modelcontextprotocol/csharp-sdk/blob/6fa3825973949a9c4f0cd8af344e15a8db09dc35/docs/concepts/tasks/tasks.md).

The released SDK does not implement task push subscriptions. The successful route uses bounded host polling at the advertised interval, outside the model. Optional `notifications/tasks` therefore does not provide the demonstrated delivery path. Unlimited default TTL omitted a required wire field in the initial probe. Finite TTL passed schema checks.

Koed's TypeScript core/server/client 2.0.0 exports older vocabulary without the selected server execution runtime. Examined release 2.2.0 retains that gap. The published extension 0.1.0 supplies no server execution/storage entry point. The merged dispatch fix in PR 2599 does not supply that missing runtime. [SDK evidence and release pins](investigations/mcp-tasks/01-sdk-route/REPORT.md), [controlled lifecycle probe](investigations/mcp-tasks/02-lifecycle-probe/REPORT.md).

Codex's one-shot synthesis helper also excludes MCP tools. Its ephemeral resume failure does not apply to the actual persistent Conversation. Managed Pi's one-shot structured-result worker likewise omits recall and exits on settlement. Neither worker substitutes for the separate persistent-host experiments.

Codex bridge output is standalone model context, not a result matched to an original MCP call. Claude host notifications and Pi custom context also differ from a second original tool result. Delivery must preserve this distinction. The model never calls a status tool in the successful bridge experiments.

The minimum demonstrated versions are SDK Tasks 2.2.0, Codex app-server 0.157.0, Claude Code 2.1.267 and Pi 0.85.1. These are tested baselines, not claims about the earliest compatible releases. Claude SDK 0.3.226 supports the altered ordinary streaming experiment, not a standard Tasks route. No minimum native-client version can be identified from this evidence.

Before a memory-dependent decision, the client must receive the result or report recall failure. Independent work can proceed while recall runs. A receipt must never be treated as evidence that memory supports the pending decision.

## Mapping to durable Personal execution

PostgreSQL remains authoritative. The SDK adapter accepts through the authenticated Local AI Runtime before creating its public receipt. Its store returns the durable UUID and delegates state reads. The SDK callback waits for the authoritative result. It does not perform synthesis, create a second queue or write competing terminal state.

| Standard concept                  | Koed mapping and evidence                                                                                                                                                                                                                                  |
| --------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Identity and duplicate acceptance | Public task ID is the durable UUID. Owner, origin and invocation identity deduplicate acceptance before admission. Repeated acceptance creates one logical task.                                                                                           |
| Working and cancellation          | accepted/running/cancel_requested map to working. Authorized explicit cancellation records intent. Disconnect only detaches delivery.                                                                                                                      |
| Completion and failure            | completed preserves JSON text, structuredContent, detail modes and Evidence Bundle. Worker application error remains completed with an error-status final question. Execution failure maps to a bounded protocol error.                                    |
| Execution and history             | Existing shared capacity, leases and generation checks remain authoritative. Fencing rejects writes from outdated execution attempts. Final question uses `memory-answer-task:<UUID>` before the terminal task link.                                       |
| Lifetime                          | Public TTL follows durable retention, normally 24 hours. Prototype expiry enforcement denies standard access after expiry. Cleanup deletes task payloads, while final Memory Question history survives.                                                    |
| Authentication and delivery       | Bind the adapter to the authenticated User. Authorize before subscription and again before result delivery. Match task, query identity, original invocation, Conversation and host generation. Experimental guards prove only their documented host scope. |
| Reconnect                         | Read current owned state, reject older versions and deduplicate `(taskId,version)`. Recovered work does not imply acknowledged or exactly-once model delivery.                                                                                             |
| Team requests                     | Canonical Team Workspace routing rejects local Personal acceptance. Team execution remains with its upstream authority.                                                                                                                                    |

[Creation/completion](investigations/mcp-tasks/10-durable-adapter/REPORT.md) passed fresh independent reproduction: seven receipts, seven final question links and shared capacity one. [Terminal cases](investigations/mcp-tasks/11-terminal-outcomes/REPORT.md) preserved selected cancellation, unrelated work, failure/error distinctions and detachment. Three cancelled tasks created no final questions in the guarded fixtures. Accelerated expiry used protected SQL timing, not a real 24-hour wait.

[Recovery](investigations/mcp-tasks/12-recovery/REPORT.md) replaced the actual runtime through four generations. Seven logical tasks linked seven final questions. Restart after question persistence reused the same question ID. Expired leases and old generations rejected late commits. This tests graceful runtime shutdown/restart, not database restart or abrupt machine loss.

The safety mapping is conditional. Existing runtime subscriptions do not satisfy its authorization and ordering requirements. The report does not certify the current implementation as safe for deferred delivery.

## Adoption blockers

The reviewed evidence identifies these requirements:

- A released maintained TypeScript Tasks server extension, or an explicit architecture decision for a maintained .NET protocol adapter. A custom dispatcher violates ADR 0043.
- Client bridges with durable pending-delivery metadata, explicit active/idle behavior and a public managed delivery seam. Native Tasks remains unproved in every tested AI Client mode.
- Controlled owner denial before subscription headers. A foreign subscription currently causes `ERR_HTTP_HEADERS_SENT` and terminates the test runtime.
- Authority revalidation before event bytes leave the runtime. Fresh revoked reads deny, but an open stream delivers an in-flight completion after revocation. The host guard prevents recipient injection only.
- A version guard and defined reconnect semantics. Actual SSE emitted versions 3, 2, 4 and replayed terminal state despite `Last-Event-ID`.
- Stable runtime/API error mapping and public expiry enforcement. Unknown API task errors became runtime HTTP 500 because `.status` was not preserved as `.statusCode`.
- Bounded diagnostics with sanitized exceptions. Normal failed-executor logs passed, but a separate real logger serializer retained supplied synthetic content in error message and stack.

[Isolation and counterexamples](investigations/mcp-tasks/13-isolation-attribution/REPORT.md) uses two real Users, separate credentials, three attributed results and ten physical ciphertext records. Its candidate preflight and per-event guards pass within their scope. They do not repair server-side stream delivery or establish general production logging safety. Ticket 13's unchecked criteria remain blockers.

The smallest next investigation is a maintained server-route decision plus a guarded adapter/delivery experiment. Retain existing execution ownership, add authorization before streaming and every delivery, then repeat the negative cases. After that, validate one natural model-initiated recall through the chosen bridge with durable delivery recovery. This report does not authorize those production changes.

## Documentation, fallback and cleanup

Clients that do not negotiate Tasks retain the existing ordinary `memory_answer` result contract. Personal execution still uses the durable owner. Host status checks remain outside the model. Claude's ordinary background behavior is a client presentation feature. Team execution remains blocking under upstream authority.

`memory_answer` is the default exposed tool. `memory_intake_propose` is capability-gated and already returns a proposal before asynchronous review. It needs a separate decision before any Tasks expansion. `memory_access_check` is diagnostic; `memory_search` and `memory_expand` are low-level tools hidden by default. No evidence justifies expanding this investigation to them. [Exposure and descriptions](../packages/mcp-server/src/index.ts), [MCP factory](../packages/mcp-server/src/mcp-server-factory.ts).

A future ADR 0043 update must identify the released contract and separate native results from standalone/custom completion context. It must retain maintained SDK adoption, Personal execution ownership and final-history rules. Capability reporting needs mode/version-specific protocol, notification, continuation and recovery fields. Claude interactive support must not be generalized to its tool-free synthesis runner. Integration documentation must describe the selected bridge, triggers, permissions, attribution, cancellation and recovery limits.

No implementation follow-up received approval. `TODO.md` and the domain glossary remain unchanged. No production architecture flow changed, so existing architecture documents need no implementation update in this research change. This report records the investigated integration boundaries.

All owned experiment services stopped. Temporary IDE folder trust was removed, and copied authentication or temporary links were removed where used. Detailed reports retain exact resource and cleanup limits. Temporary build and synthetic evidence remain for review. Existing ignored investigation artifacts were not force-added. The User confirmed no changeset for research artifacts. No deployment, package release or external publication occurred.
