# Share Project sheet (HQ701)

The HQ Share action opens a review sheet for one Personal Project. It shows the destination Team, the existing members, and the exact first-share disclosure before it creates a Team Workspace Project. The Desktop requires an active, verified Team principal on the selected backend. Koed managed cloud is the default target; an advanced `team_self_hosted` backend is eligible with the same verified WorkOS enrollment. A `private_vps` backend cannot start this flow. The release must configure a trusted hosted Team target; this repository does not contain a canonical production cloud URL. Until it is configured and enrolled, the sheet shows readiness and makes no sharing write.

The first share uses the HQ712 owner-local copy manifest and Team authority. The Personal attempt stores its backend, idempotency key, exact Team, and exact Workspace before the copy begins. A restarted Desktop reads that attempt through the owner-scoped local edge, which checks the enrolled Team principal and current write access to the target. It resumes the same target and key. A different target or key conflicts. Historical attempts without a stored target require explicit recovery and are never guessed from Team names. The Team backend receives Work Items and Source metadata, including the uploader's real Personal Note identity and revision where present. Original file bytes, Note text, Personal Project IDs, private Agent Conversations, and Curated Memory stay outside the Team copy. A Chat summary needs separate owner-consented sharing; opening the sheet does not grant or publish it.

The owner can cancel a pending first share in the sheet. The Team first records an immutable receipt for the exact enrolled member, Workspace, and attempt key while holding the Workspace creation lock. Team creation rejects that key after the receipt, including delayed requests. If the Project was already created, cancellation conflicts and the owner resumes reconciliation. The Personal attempt changes to canceled and releases its local edit fence only after the exact Team receipt returns. An offline or uncertain reply leaves the attempt pending; retry uses the same key and receipt. Starting again requires an explicit new attempt key.

If Team creation committed but Personal confirmation did not, later Team access loss or Project deletion leaves the Personal attempt pending. Current recovery requires current Team authority; a missing Project or unavailable backend is not evidence that cancellation succeeded. The shared Project lifecycle integration must add exact receipt-based recovery for this window before final cutover, without widening access to retained Team content. A lost reply after Personal confirmation committed follows the existing linked-Project reconciliation path. The remaining implementation and regression work is recorded in `TODO.md`.

The “Who’s in” list reads current Workspace Project associations through the Team backend and counts enabled members with current Workspace Access. It does not count pending invitations. The Share sheet can issue the existing Native-reviewed Team invitation with an optional exact Workspace Project handoff ID and reviewed version. The Team invite transaction checks that its manager is also the current Project owner; ordinary Team managers keep their existing generic invitation authority, and a Project owner who is not a Team manager gains no Team invitation authority. The handoff is stored on the invite for HQ703 to consume after verified acceptance and renewed Project authority checks. HQ701 does not create the recipient's Project association when merely issuing an invitation, so the pending invitation is displayed separately from active membership.

The command palette accepts “Share <Project name>” and opens the same sheet. It does not bypass destination review or create a Share Grant. HQ702 owns the per-member summary policy; HQ703 owns recipient acceptance and Project association. No live cloud enrollment or invitation is exercised by fixture tests.

The Project invitation handoff is retained in the Team record and bound to the exact reviewed create operation. Existing v1 invitation responses and collaboration snapshots omit that field, including when the internal handoff is nonempty. Recipient Project admission uses an explicit later protocol; strict legacy clients receive their existing invitation shape.
