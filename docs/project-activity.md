# Personal Project activity

The backend keeps deterministic, owner-scoped Project activity for the HQ sparkline and catch-up. `project_activity` stores the actor User ID, kind, stable source reference, server timestamp, and a per-Project sequence. `project_seen` stores the owning User's highest acknowledged sequence. Both tables are Personal records; linking a Project to a Workspace Project does not publish these rows to the Team backend.

The existing HQ summary now includes `activity.lastSevenDays`: seven UTC calendar-date buckets including today. The first bucket starts at 00:00 UTC six dates before today, and the last ends at the server's current instant. Future rows do not count. `total` is the sum of those seven buckets. The field is additive to the existing strict HQ response contract.

`GET /v1/projects/{id}/activity?after=<cursor>&limit=100` returns rows in ascending sequence, with an opaque cursor on each row and `nextCursor` for the last returned row. A client can read after its saved cursor and filter already visible PRs and completed tickets for HQ-505. `GET /v1/projects/{id}/activity/seen` returns the saved cursor; `PUT` to the same path with `{ "cursor": "..." }` advances it. Reading does not mark activity seen. The HQ opener should acknowledge the last row it actually displayed, using its returned cursor. An empty Project's initial cursor can be read from `/seen`. Cursors are bound to the exact owner and Personal Project; acknowledgements require a committed row and cannot rewind. Deleted Projects deny normal reads and writes; retained activity and the seen cursor survive restore.

Desktop exposes these operations through the validated Projects IPC as `activitySeen`, `activityPage`, and `activityAcknowledge`. The main-process client pins the current Personal owner/profile authority across each request, and preload correlates the Project ID in each response. Opening HQ reads a bounded residual window from the saved cursor without acknowledging it. A trusted, server-built `hq_catch_up` command binds that window to the current owner, Project, execution generation, and provider turn. Its synthetic instruction is excluded from visible User turns only after verified command correlation. The AI Client runs the command with restricted tools; the exact high-water mark is acknowledged only after its assistant reply is durably captured. Failed, uncertain, or unacknowledged turns keep their window for reconciliation without automatic replay. Extraction outcomes use an attempt ID, not a Source ID. The activity read enriches an outcome only when the owning Project Source repository proves the attempt still belongs to the active Project and is its current ready or failed revision; stale or removed outcomes are omitted from residual catch-up input.

Session or enrolled device credentials authorize these routes with Personal collaboration read or write authority. Existing local Desktop credentials may read on loopback under the Project read policy; they do not gain write authority. API Tokens remain rejected. There is no client append endpoint. Trusted writers call `appendProjectActivityWithClient` in the same database transaction as their source mutation after acquiring the owning Project row `FOR UPDATE`. This lock gives per-Project sequence order the same order as commits, including concurrent writes and seen acknowledgements. Source retries use stable `(kind, ref)` values to avoid duplicate rows.

Current writers cover Work Item creation, changed status, completion, Project Source creation, current Source extraction outcomes, verified PR opened/merged transitions, and committed Project-scoped Curated Memory decisions. The append hook requires the actor to be the owning User. Extraction outcome references are attempt IDs; the catch-up reader resolves each attempt back to the latest current Source and revision before using it. The Curated review adapter locks the active owning Project without waiting, then commits the assertion and exact Project activity in one transaction. Catch-up excludes revoked, superseded, or wrong-scope assertion evidence. Team collaboration activity belongs on the Team backend; member events are rejected by the Personal hook. Team Chat Messages are neither Project activity nor Memory or agent input.

The HQ header uses `activity.lastSevenDays.outcomes`: separate counts of completed Work Items (`work_item_done`) and merged pull requests (`pr_merged`), plus seven daily buckets containing only those outcomes. It uses the same server clock, UTC bounds, and owner/active-Project fence as the existing all-activity `days` and `total`; other kinds do not inflate completion or merge counts. This optional extension preserves older HQ responses. A client connected to a server without outcomes shows those metrics as unavailable. Reads do not acknowledge activity.

## Workspace Project member frontier

The Team backend keeps a separate `workspace_project_seen` cursor for each exact Workspace Project and current Team membership. A new member's initial cursor starts after activity committed before their Project association. A current Project member with Team Workspace read access can read its cursor and a bounded page of public Project activity through `/v1/workspace-projects/{id}/activity/seen` and `/v1/workspace-projects/{id}/activity`. The page contains only an actor member ID, one of the public Work Item, Source, or merged PR kinds, a reference, and a server timestamp. It contains no Team Chat Message content. The member's acknowledgement is monotonic and must name a committed Project event. A separate `welcomeDeliveredAt` marker records a welcome once for that membership; it does not advance the activity cursor. Project or Workspace access revocation denies both reads and acknowledgement. Team Chat unread state remains separate.

The Personal backend cannot read this Team cursor directly. The local Desktop coordinator uses the currently enrolled, backend-qualified sealed Team credential and an exact linked Workspace Project to read an immutable public activity window. Catch-up includes only eligible new Work Item and Source counts and a one-time welcome; completed Work Items and merged pull requests are already visible in HQ and stay out of the AI instruction. The terminal receipt retains the window and rechecks the current link, principal, and membership before an idempotent remote acknowledgement. A lost acknowledgement response is reconciled against the exact cursor without generating another AI turn. Team Chat unread state remains separate and no Team Chat text enters the Personal catch-up prompt.
