# Flashcard Deck storage and API

A Flashcard Deck is Project work state. Deck titles, scope, provenance labels, and question-and-answer cards are collaboration records, not Memory. `source_ref` is a display label; it grants no access to a Project Source, citation, or Personal record. Creating cards requires supplied content. Generation through an AI Client belongs to HQ-802.

Private Projects store decks and cards in the Personal database. A linked Project stores its active deck and card content in the Team database under its Workspace Project ID. Personal Project IDs never identify Team Projects. The first-share copy uses the trusted owner-local snapshot and an idempotent Team copy; the Team backend returns an owner-only deck/card identity map so only that owner's existing study progress can follow the copied cards. Each member's study progress remains in their own Personal database. Team routes never read progress, and the Team copy/copy-back payloads contain no study progress or Me learning.

The Personal API uses `/v1/projects/:projectId/decks` for private content and `/v1/projects/:projectId/deck-progress` for private study state. The Team API uses `/v1/workspace-projects/:projectId/decks` for shared content. Shared progress reads and writes pass through `/v1/local-edge/projects/:projectId/decks/:deckId/...` with the owner's local Desktop credential, enrolled Team client credential, the exact Personal-to-Workspace Project link, and live Team read authority. Read-only Project members may study. The backend validates the requested card against the live Team Deck and checks the current link again before writing progress. An unavailable Team backend denies shared progress access. Personal API Tokens do not authorize these Project operations. Requests have no user selector for another member's progress.

Deck creation requires an `idempotencyKey` and persists a payload hash. An exact retry returns the original Deck; changed content with the same key conflicts. Deck and card edits require optimistic versions. Project change and Workspace Project change events tell clients to refetch Decks; progress writes produce no Team activity. `created_by_agent_id` is an owner-scoped Personal Agent reference in the Personal database. On first-share copy the Team row retains it only as opaque provenance paired with the authenticated creator member; new Team Deck creation leaves it null. It confers no Agent authority.

Personal Project delete/restore includes its Decks in the exact batch. Team Project deletion soft-deletes its Decks and blocks normal Deck and progress reads. An owned Project's Team leave stages a bounded Deck/card snapshot, then copies it back idempotently to that owner's Personal Project. The owner's progress is remapped where the copied card identity is provable. Another member's progress is never copied. The study scheduling algorithm and Again-to-Me learning are HQ-803 work.

## AI Client generation

`koed_deck_make` is a managed Conversation text action. The AI Client reads authorized current Project Sources through `flashcard_sources` and uses `memory_answer` for relevant exam scope, learning preferences, and weak spots. It supplies the Deck title, explicit study scope, source description, and question-and-answer cards. For example, “chapter 7, excluding topics not on the midterm” stays a distinct Deck scope. Answers may include citations; a card's `sourceRef` is only a display label. Project Thread messages and another User's private material are not generation input.

Koed accepts a proposal only from the current leased human-started turn. It verifies that the proposed Project is the current Conversation's Project, resolves the Agent from the bound AI Client instance, snapshots current Project and Team authority, and shows the exact card content for Ask first review. The action ID becomes the Deck creation key. A Personal Deck write verifies the claimed action inside the Deck transaction. A Team Deck write uses the enrolled device principal and current Personal-to-Workspace Project link; the journal records a one-way dispatch marker before the Team request. An uncertain Team outcome is reconciled by an authorized read of the creation key and never causes an automatic second create request. New Team Decks keep `created_by_agent_id` null until a separate trusted Team provenance contract exists.

After a verified effect, the action card resolves `{ projectId, deckId }` through a read-only receipt. `projectId` is always the owner's Personal Project ID for navigation. A Team Deck ID is resolved against the current link and live Team access. A Deck copied from Personal storage on first share resolves through its `source_deck_id` mapping, so its earlier action card still opens the shared copy.

The Team receipt also binds the original runner device, the authenticated enrolled device credential, and `team_workspace_write` scope. After a Team-generated Deck is copied back during leave, the former Team action card does not infer a new Personal Deck ID from a matching creation key; it reports the Deck unavailable unless an exact current mapping exists. The Deck remains browsable from the Personal Project.
