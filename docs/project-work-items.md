# User-owned Project Work Items

Work Items are to-dos or tickets owned by a User's active Project. They are operational state, not Memory. `due_on` is a calendar date (`YYYY-MM-DD`), without a time or time zone; each viewer interprets that date locally.

`GET` and `POST /v1/projects/{id}/work-items`, `PATCH` and `DELETE /v1/work-items/{id}` require a browser session or a local device credential with `personal_collaboration_read` or `personal_collaboration_write`. Personal API Tokens do not authorize these operations. Every repository operation verifies the current owner and active Project. Projects with an authoritative Team link are unavailable here; HQ-712 owns their Team-side state and access rules. The recall-routing configuration is not a Team link.

Interactive `POST` accepts the item's kind, optional ticket key, title, goal, a `manual` origin, optional idempotency key, and optional due date. It cannot claim a document or runtime origin. Trusted future integrations may supply a verified source revision through the repository. The `(owner, Project, origin, idempotency_key)` identity replays an exact creation. Reuse with a different payload returns `409` and the current Work Item. Deleting a to-do retains a hidden tombstone and its idempotency identity. For a creation with an idempotency key, an exact delayed replay returns `410 Gone`, while a drifted replay returns `409` with `current: null`. The helper `workItemPlanLineKey(sourceRevisionId, line)` normalizes each line and hashes it with its source revision for HQ-406; HQ-406 must derive this key from verified source material rather than trusting renderer text. The `workItemDispatchKey(itemId, versionAtSend)` helper establishes the HQ-404 dispatch identity.

`PATCH` requires the current positive `version`. A stale version returns `409` with `current`. Browser actions can edit title, goal and due date, mark done from any state, untick done to todo, or move blocked back to todo. `DELETE` accepts to-dos only. Assignee, execution, dispatch, PR status, and automatic transition fields are absent from the public write contracts.

`GET /v1/projects/{id}/work-items` returns `{ items, hasMore, nextCursor }` in newest-first order. The optional `limit` defaults to 100 and can be 1–1,000. When `hasMore` is true, pass the opaque `nextCursor` as the next request's `cursor` with the same Project. Cursors are versioned and scoped to the authenticated owner and Project; malformed or foreign cursors return `400`. The keyset retains PostgreSQL's full timestamp precision and uses the item ID to break ties, so equal creation times do not hide items. Clients should stop when `hasMore` is false. A re-list after a realtime `requires_snapshot` starts without a cursor and follows pages as needed.

The server transition table is implemented by `nextWorkItemStatus` and persisted through `transitionTrusted`, which locks the owner, active Project, and Work Item; checks the expected version and exact execution/PR binding; and commits state and the realtime outbox together. Its evidence verifier is injected by a trusted service and is absent in production until HQ-404/HQ-405 connect authoritative execution and provider evidence. Future verifiers must use bounded server-persisted evidence, not outbound provider calls while the database locks are held. No public route can claim such an event. In particular, a PR closed without merging transitions from review to blocked, never automatically to done. A User can still explicitly mark that blocked item done. The planned dispatch and retry flows require HQ-404's verified binding to an Agent and Managed Conversation; no arbitrary IDs are accepted now.

Mutations append a personal `work_item_changed` event in the same database transaction. PostgreSQL delivers its notification after commit. The existing collaboration realtime stream re-reads the current item for the authenticated owner and active User-owned Project before sending a typed record with its version. Deleted or newly unavailable items produce `requires_snapshot`; after reconnect, the consumer must re-list the Project with `GET /v1/projects/{id}/work-items` to remove stale rows. The realtime snapshot does not itself contain Work Items. Team streams receive no Work Item payload from this Personal path. HQ-206 owns durable Project activity rows; this ticket does not create them or claim that they are available.

The flagged Desktop Project HQ reads every Work Item page through its owner-bound Projects client. It groups to-dos, in-progress items, review items, blocked or due-soon items needing attention, and items completed on the viewer's local calendar day. The add field accepts the shared due-date phrases, including “by Friday”; completion and moving a blocked item back to To do use versioned writes. A retry of an unacknowledged creation reuses its idempotency key. The displayed activity sparkline comes from the Project HQ activity endpoint, not from provisional renderer counts. Dispatch, live Work Item logs, and PR merge readiness depend on later runtime/source-control tickets and are not inferred from an open PR record.
