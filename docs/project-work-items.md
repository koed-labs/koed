# User-owned Project Work Items

Work Items are to-dos or tickets owned by a User's active Project. They are operational state, not Memory. `due_on` is a calendar date (`YYYY-MM-DD`), without a time or time zone; each viewer interprets that date locally.

`GET` and `POST /v1/projects/{id}/work-items`, `PATCH` and `DELETE /v1/work-items/{id}` require a browser session or a local device credential with `personal_collaboration_read` or `personal_collaboration_write`. Personal API Tokens do not authorize these operations. Every repository operation verifies the current owner and active Project. Projects with an authoritative Team link are unavailable here; HQ-712 owns their Team-side state and access rules. The recall-routing configuration is not a Team link.

Interactive `POST` accepts the item's kind, optional ticket key, title, goal, a `manual` origin, optional idempotency key, and optional due date. It cannot claim a document or runtime origin. The `(owner, Project, origin, idempotency_key)` identity replays an exact creation. Reuse with a different payload returns `409` and the current Work Item. Deleting a to-do retains a hidden tombstone and its idempotency identity. For a creation with an idempotency key, an exact delayed replay returns `410 Gone`, while a drifted replay returns `409` with `current: null`. The `workItemDispatchKey(itemId, versionAtSend)` helper establishes the HQ-404 dispatch identity.

For a ready document Source, the top action asks the actual Chief of Staff to turn that document into tickets or to-dos. The visible User message is short, for example **Turn Plan.md into tickets**. Koed sends the selected Source ID separately as typed, owner-verified managed-command context; the ID and tool instructions are not inserted into the User message. For a typed chat request without a selected Source, `work_items_from_doc` first lists bounded current readable document metadata so the AI Client can choose an exact ID or ask the User about ambiguous names. A selected command lists only its bound document. The connected AI Client then reads every page (without a `source_id` when the command has a selected document), decides which exact lines describe actionable work, and submits a structured proposal through the same tool. A to-tickets skill may guide that decision but is not required. The tool's apply result is only a request receipt. The Worker uses its live command lease to ask the local API to validate and create the batch. No API backend model processes the document, and the renderer cannot submit document-origin Work Items.

The read stage requires the local Desktop credential, the current owner, execution generation and dispatching command lease. It returns at most 200 lines and 32,000 characters per page, with an explicit next cursor and remaining indicator. A line longer than the 4,000-character evidence bound rejects the document before any page is shown. The apply transaction locks the active Personal Project, exact current Source and Note revision, managed execution and command; it verifies every proposed line number and verbatim line against the decrypted Note, checks due text within that line, and rechecks the lease before commit. If a concurrent human prompt owns the execution lock, apply returns a conflict immediately and rolls back the whole batch; it never waits while holding the Project lock. It chooses tickets when the Project has a ready repository Source and to-dos otherwise. `workItemPlanLineKey(sourceRevisionId, line)` normalizes the verified source line and hashes it with its revision. A rerun of the same revision adds nothing even if the AI Client changes a generated title; a new legitimate revision has independent keys. Missing, forgotten, foreign, linked, or changed Sources and stale commands fail without creating items.

`PATCH` requires the current positive `version`. A stale version returns `409` with `current`. Browser actions can edit title, goal and due date, mark done from any state, untick done to todo, or move blocked back to todo. `DELETE` accepts to-dos only. Assignee, execution, dispatch, PR status, and automatic transition fields are absent from the public write contracts.

Unticking or returning an item to To do cannot detach a still-running Agent. Koed first requires the linked execution to be stopped, failed, or fenced, so a later Send cannot silently start a second Agent while the first is active.

`GET /v1/projects/{id}/work-items` returns `{ items, hasMore, nextCursor }` in newest-first order. The optional `limit` defaults to 100 and can be 1–1,000. When `hasMore` is true, pass the opaque `nextCursor` as the next request's `cursor` with the same Project. Cursors are versioned and scoped to the authenticated owner and Project; malformed or foreign cursors return `400`. The keyset retains PostgreSQL's full timestamp precision and uses the item ID to break ties, so equal creation times do not hide items. Clients should stop when `hasMore` is false. A re-list after a realtime `requires_snapshot` starts without a cursor and follows pages as needed.

The server transition table is implemented by `nextWorkItemStatus` and persisted through `transitionTrusted`, which locks the owner, active Project, and Work Item; checks the expected version and exact execution/PR binding; and commits state and the realtime outbox together. Its evidence verifier is injected by a trusted service. No public route can claim such an event. In particular, a PR closed without merging transitions from review to blocked, never automatically to done. A User can still explicitly mark that blocked item done.

`POST /v1/projects/{id}/work-items/{itemId}/dispatch` takes a chosen User-owned Agent and the current Work Item version. It is available only for a local Project with a verified execution path and a ready AI Client instance. While remote Managed Conversation authority is active, the route returns `503` before changing state because this local atomic binding cannot be claimed by the remote worker. The server selects that Agent's registered AI Client and model; the renderer supplies neither. The active Project is locked before the Work Item. The managed start command and Work Item's `execution_id`, `dispatch_key`, assignee, and `doing` state commit in one transaction. Concurrent Send requests for the same Agent return the same Managed Conversation; if runtime binding was interrupted after commit, a repeat Send reconciles it only on the original runner device. The first prompt carries the Work Item goal, bounded owner-authorized Project Source references and readable document excerpts, and an instruction to call project-scoped `memory_answer` for related Personal Memory. Team messages are excluded.

The dispatch transaction checks that each included Source remains ready, active, owner-matched, and at the exact Note revision read for the brief. A removed or forgotten Source aborts dispatch before its prompt can reach an Agent.

An explicit Send to someone else queues an idempotent stop of the current execution. Koed does not launch the replacement while the prior execution is still active. Once the prior execution reaches a terminal state and the Work Item is blocked, the User can send it to the new Agent. Retry with the same Agent advances the managed execution generation and queues one new turn in the same Managed Conversation. If the earlier attempt had no provider thread, Retry revalidates the encrypted original Source revision proof before replaying its first prompt; a removed or forgotten Source returns `409` without queuing another start. An indeterminate first start requires read-only reconciliation. Old command leases cannot complete a retried Work Item.

The `work_item_complete` tool is presented through MCP or the native Pi integration only to managed Work Item sessions and returns a completion request. The worker observes a successful Koed tool result and calls the repository's `completeFromManagedCommandLease` with its own active command lease. This requires the current Work Item version, the same owner, Project, execution, and execution generation, and no linked PR. Client-supplied execution IDs alone grant no authority. Listing Work Items reconciles terminal failed, stopped, or fenced Managed Conversations to `blocked`; pending approvals keep the item in `doing`.

When the native source-control runtime completes `review_request_create`, its verified provider result links the PR URL and number to the current dispatched execution and moves the Work Item to `review`. The runtime first persists its idempotent operation journal, then invokes the Work Item observer; an exact replay reapplies a missed link without creating another PR. The observer rejects stale execution generations, unrelated owners, and conflicting PRs. Later merge and closure tracking belongs to the source-control lifecycle.

Mutations append a personal `work_item_changed` event in the same database transaction. PostgreSQL delivers its notification after commit. The existing collaboration realtime stream re-reads the current item for the authenticated owner and active User-owned Project before sending a typed record with its version. Deleted or newly unavailable items produce `requires_snapshot`; after reconnect, the consumer must re-list the Project with `GET /v1/projects/{id}/work-items` to remove stale rows. The realtime snapshot does not itself contain Work Items. Team streams receive no Work Item payload from this Personal path. Durable Project activity records are published separately from these realtime notifications.

The flagged Desktop Project HQ reads every Work Item page through its owner-bound Projects client. It groups to-dos, in-progress items, review items, blocked or due-soon items needing attention, and items completed on the viewer's local calendar day. The add field accepts the shared due-date phrases, including “by Friday”; completion and moving a blocked item back to To do use versioned writes. A retry of an unacknowledged creation reuses its idempotency key. The displayed activity sparkline comes from the Project HQ activity endpoint, not from provisional renderer counts. Its send arrow opens an Agent menu and its work brief displays goal and runtime items from the linked Managed Conversation. PR merge readiness depends on the later source-control ticket and is not inferred from an open PR record.

Only a currently active, locally bound Work Item execution receives the `work_item_complete` tool in its Codex, Claude Code, or Pi child environment. The worker checks the owner, execution and generation before setting the presentation flag; ordinary and auxiliary sessions have any inherited flag removed. The flag is not authority. Completion still requires the trusted transport callback and the exact live command lease. Remote authority mode does not expose this local completion path.
